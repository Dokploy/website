Manage Docker Swarm secrets from **Docker > Swarm > Secrets**. Create a secret once, then reference its name in the stacks that need it. The **Overview** tab also shows a **Total Secrets** card for the selected server.

## Requirements

- Select an active **Swarm manager** in the server selector. Workers cannot manage secrets.
- Your account needs the **Docker** permission and access to the selected server. The page uses the same access checks as the other Docker tabs.
- Create the secrets on the same Swarm that deploys your stack. For remote deployments, select that remote Swarm manager. Dokploy Cloud users must select a remote server.

Secrets belong to the whole Swarm. The list includes secrets and service references created outside Dokploy. It is not limited to the current project or environment. Choose names that are safe to show to users with Docker access.

<Callout type="info">
  Swarm secrets are different from [Secrets Providers](/docs/core/secrets-providers). Swarm secrets are mounted as files into Swarm services. Secrets Providers resolve references from external vaults into deployment configuration.
</Callout>

## Create a secret

1. Open **Docker > Swarm > Secrets** and select your server.
2. Choose **Create secret**.
3. Enter the **Content** in the editor and choose a unique **Name**.
4. Choose **Create secret** to save it in Docker Swarm.

Names must start with a letter or number and contain 1 to 64 letters, numbers, dots, underscores, or hyphens. Include an environment or version in the name when useful, for example `mysql_password_production_v1`.

Content supports UTF-8 text, including multiline keys. It must be non-empty and smaller than 500 KiB, with a maximum of 511,999 UTF-8 bytes. Spaces and newlines are preserved. The form does not support binary file uploads.

<Callout type="warning">
  Docker's secret management API does not return the content after creation. Dokploy does not store another copy, so there is no view or edit action. Keep a separate copy in your password manager if you need one. Use HTTPS when entering secret content in Dokploy.
</Callout>

## Use secrets in a stack

Select the **Stack** deployment type for your [Docker Compose service](/docs/core/docker-compose). Ordinary **Docker Compose** deployments cannot consume secrets stored in Docker Swarm.

Create the application and root password secrets first. In your stack's **Environment** tab, set these variables to the existing **secret names**, not their values:

```dotenv
MYSQL_PASSWORD_SECRET=mysql_password_production_v1
MYSQL_ROOT_PASSWORD_SECRET=mysql_root_password_production_v1
```

Add these fields to your existing MySQL stack. Keep its image, database, user, persistent storage, and other required settings:

```yaml
services:
  mysql:
    environment:
      MYSQL_PASSWORD_FILE: /run/secrets/mysql_password
      MYSQL_ROOT_PASSWORD_FILE: /run/secrets/mysql_root_password
    secrets:
      - mysql_password
      - mysql_root_password

secrets:
  mysql_password:
    external: true
    name: ${MYSQL_PASSWORD_SECRET:?Set the application password secret for this environment}
  mysql_root_password:
    external: true
    name: ${MYSQL_ROOT_PASSWORD_SECRET:?Set the root password secret for this environment}
```

Deploy the stack after saving the changes. The service-level `secrets` entries grant the MySQL service access to the files. Top-level declarations alone do not grant access. The file names above use the Compose keys, while `name` selects the existing Swarm secret for each environment.

`external: true` is a setting in the stack's Compose file. It tells Docker to use an existing secret instead of creating one during deployment. It is not a property you set when creating a secret in the dashboard.

Your application must support reading the mounted files. MySQL supports the `_FILE` variables above; other images may use different settings. Avoid putting the actual password in the stack's environment variables.

The **Use in a stack** button opens an example. It does not change or deploy any stack and does not attach secrets automatically.

## Check service usage

The table shows the secret's name and ID, the number of services using it, service references, and its creation date. Use the copy icon beside the name to copy the exact name into your stack configuration.

**Used by** counts distinct Swarm services. If three services in one stack reference a secret, the count is three. A service referencing the secret in both its current and rollback settings counts once. Services scaled to zero still count.

The **Service references** column shows service names and their stack names when available:

| Label | Meaning |
| --- | --- |
| Current | The service's current configuration references the secret. This does not mean its containers are healthy or running. |
| Rollback | The service's previous configuration still references the secret for rollback. |
| Current and rollback | Both configurations reference the secret. |
| Unused | No current or rollback service configuration references the secret. |

Usage comes from the selected Swarm's deployed services, including services outside Dokploy. It does not scan saved Compose files that have not been deployed. A top-level declaration without a service-level reference does not count as usage.

Search by name, ID, service, or stack. Sort by name or creation date using the table headers. **Created** shows the date and relative age; **Actions** is the last column. Use **Refresh** after making changes outside Dokploy.

If Docker cannot return the list, Dokploy shows an error instead of treating secrets as unused. If the overview count cannot be loaded, **Total Secrets** shows **Unavailable**.

## Delete a secret

1. Remove the secret from every service configuration that references it and redeploy the affected stacks.
2. Check that no rollback configuration still needs it.
3. Refresh the list. Once **Used by** shows zero, choose the delete icon.
4. Type the exact secret name in the confirmation dialog and choose **Confirm**.

Deletion is blocked while any current or rollback service configuration references the secret, including services scaled to zero. Hover over or focus the disabled delete icon to see the reason.

Dokploy checks the secret ID, confirmation name, and live service references again when you confirm. Docker also checks whether the secret is in use. Dokploy does not stop services or remove their references for you. Deletion cannot be undone.

## Rotate a secret

Swarm secret content cannot be changed in place:

1. Create a secret with new content and a new name, such as `mysql_password_production_v2`.
2. Update the stack's secret-name environment variable and redeploy it.
3. Verify that the application can use the new secret.
4. Delete the old secret only after all current and rollback references have been removed.

<Callout type="warning">
  Replacing a mounted MySQL password file does not change an existing database account's password. Follow MySQL's password rotation procedure too, and keep the database credentials and mounted files in sync.
</Callout>

## Troubleshooting

- **Secret not found during deployment:** Check the selected Swarm, the exact secret name, and the stack's environment variables. A secret created on another Swarm is not available to this stack.
- **Service cannot read the secret:** Check its service-level `secrets` entries, expected file path, and file permissions for the container's user.
- **Delete stays disabled:** Check both current and rollback references, including services scaled to zero. Stopping containers alone does not remove their service configuration.
- **Manager or connection error:** Select a Swarm manager and check the server's connection and your access to it.

See [Docker secrets](https://docs.docker.com/engine/swarm/secrets/) for storage, mounting, and rotation details.
